PyTorchSim 编译器修改维度全景

1. 背景与范围

Route 4 的目标是从 tiling-only search space 扩展到更接近真实编译器控制面的修改维度，判断 PyTorchSim 上是否存在 measured HW/SW co-design POSITIVE 证据。

证据链从 v1 NEGATIVE 开始：92623de 在 GPT-2 single block prefill seq=128 的 tiling-only 2x2 SPAD/BW 空间上得到 NEGATIVE，09b9ac3 在 10% Gate-1 threshold 下重算后仍保持 NEGATIVE。随后 42e57b6 做 Route 4 discovery，确认 fusion 是无需源码修改即可切换的编译器轴，而 dense systolic dataflow 不是 YAML 暴露轴。最终 79e6259 在 Conv 3x3 workload 上得到 FUSION_CONV_CODESIGN_POSITIVE：fusion speedup across HW 的 relative range 为 42.7%，gate2b_ratio_fusion=0.523。

本文只总结当前可实现的编译器修改维度，不新增 TOGSim sweep，不修改 PyTorchSim / TOGSim / gem5 / ramulator2 / spike 源码。

3. Fusion 维度深入

Fusion 是当前唯一已经跑通并产生 POSITIVE 的 compiler axis。42e57b6 的 discovery 确认 fusion 控制面来自 codegen_compiler_optimization，配置可设为 all、none 或部分 fusion family。限制是：它不是任意 pattern-level 开关，template-template fusion 被禁止，Conv 主要支持 epilogue fusion。

  • 59f44ba recovery 后，addmm+relu 128 在 mode=0 timing 下出现强信号：fusion=none median 2183 cycles，fusion=all median 1118 cycles，约 2x。
  • 3489f94 在 GPT-2 block seq=128 上做 fusion x HW mini check：fusion=none median 430717，fusion=all median 422711，差异只有 1.9%。
  • ce5f0e3 做 root-cause investigation：GPT-2 structural diff 显示 fusion=all 的 MLIR op count 比 fusion=none 少约 7.8%，但该变化不在 GPT-2 主导 critical path 上。Conv 3x3 single-cell probe 显示约 6.84x。
  • 79e6259 的 Conv 4-HW x 2-fusion sweep 得到 FUSION_CONV_CODESIGN_POSITIVE。四个 HW 的 fusion speedup 为：HW-A=6.895x，HW-B=4.830x，HW-C=6.262x，HW-D=5.253x。

结论：fusion 轴是实测有效的，但其价值高度 workload-dependent。GPT-2 block 上弱，Conv-heavy workload 上强，并且在 Conv 上与 HW 配置存在 measured interaction。

4. Dataflow 维度死锁

42e57b6 的 discovery 已确认 dense systolic main path 实际上是 weight-stationary。搜索未发现 output_stationary / input_stationary / dense systolic dataflow YAML selection。STONNE sparse path 中存在 dataflow enum，但它属于 vendored STONNE path，不是 PyTorchSim dense WS_MESH systolic path 的无源码配置轴。

因此 dataflow 当前是 BLOCKED without source modification。若未来要纳入 Route 4，需要新增 YAML field、extension config plumbing、GEMM/BMM/SDPA loop order 和 tile descriptor generation，还要检查 TOG generation / gem5 cycle sampling 是否含 weight-stationary assumption。

5. SPAD partition 维度

Task 1 discovery 只做只读 grep，没有运行 TOGSim sweep。configs 中存在 vpu_spad_size_kb_per_lane，这是容量轴，不是 partition policy。Conv templates 明确创建 input_buffer、weight_buffer、output_buffer；BMM/GEMM 类 template 也采用固定的 SRAM buffer 命名，例如 X_buffer、W_buffer、Y_buffer。

判定：SPAD_PARTITION_HARDCODED。当前可以 sweep SPAD 容量，但不能无源码地表达 input/weight/output/intermediate 的分区策略。

6. DMA schedule 维度

Task 1 discovery 未发现 prefetch、double_buffer、async_wait、dma_schedule、dma_pipeline 等 YAML/CLI 控制字段。format_dma_op_attributes() 支持 memref.dma_start 的 async attribute，但具体插入顺序由 dma_loads / dma_stores buffers 和模板 splice 逻辑决定。

判定：DMA_SCHEDULE_HARDCODED。若未来要把它变成 Route 4 轴，需要暴露 prefetch/double-buffer/wait policy，改 DMA insertion order，并验证 raw TOG / ONNX TOG 的 wait dependency。

7. 未来 Route 4 扩展建议

  1. Fusion x HW at multiple mappings：在 Conv-heavy workload 上加入多个 mapping，观察 champion migration 和 ranking correlation。
  2. Fusion x HW on additional Conv-heavy workloads：用 ResNet-50 stage、MobileNet depthwise/pointwise block 或 Conv-BN-ReLU stack 验证泛化。
  3. SPAD partition axis or DMA schedule axis：当前 discovery 判定二者都不是 YAML controlled。若接受源码修改，优先选择改动范围更清楚的 DMA schedule。
  4. Dataflow axis：只有在接受较高源码修改成本后再做。

最终建议：短期 Route 4 应继续围绕 fusion axis 做 workload 和 mapping 扩展；不要把 Conv POSITIVE 直接泛化到 GPT-2 或所有 NPU workload。
